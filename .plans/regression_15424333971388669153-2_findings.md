# Regression divergence: `15424333971388669153-2.pdf` (macOS vs Ubuntu)

## Symptom

`tests/test_regression_parse.py::test_reference_documents_from_filenames` fails on
Ubuntu (passes on macOS) with 24 page failures, all on
`./tests/data/regression/15424333971388669153-2.pdf`:

```
E  AssertionError: 24 page(s) failed: ...@1[char], ...@1[word], ...@1[line], ...
E  assert 24 == 0
```

The 24 is **not** 24 unrelated failures. It is the **same two page-repeated
elements** (a header line + a footer line) × 3 units (char/word/line) × 4 pages
= 24. Per page: exactly **61 fewer char cells, 1 fewer word, 1 fewer line**.

## Root causes

There are two distinct causes.

### 1. Header line — `の` vs `䛾` (stale groundtruth; current code is *correct*)

The header line decodes differently:

| | text | font_key | font_name |
|---|---|---|---|
| **Current (Linux)** | `■業績の概要とカーボンニュートラル化に係わる取り組みの要旨` | `/R9` | `/HZHHNL+…` (raw Shift-JIS, renders as mojibake) |
| **Groundtruth (macOS)** | `■業績䛾概要…取り組み䛾要旨` | `/G1` | `/AAAAAB+font00000000303895f2` (synthesized) |

The font `/R9` is a Type0 / CIDFontType2 (Identity-H) with a `/ToUnicode` CMap
that contains the bfrange:

```
<46fe><47ff><306e>      # CID 0x46FE → U+306E (の)
```

So `の` (U+306E) is the **correct** decoding. The groundtruth's `䛾` is U+46FE —
i.e. the **raw CID value used directly as a codepoint**, the old bfrange-lookup
bug that commit `3a952bb` ("fixed the accents", which rewrote
`src/parse/pdf_resources/page_font/font_cid.h` and cmap handling) fixed.

Supporting evidence:

- The **original PDF** page-1 font resource key is `/R9`, with a BaseFont name
  that contains Shift-JIS bytes (byte `0x82`). The current code faithfully
  preserves `/R9` and the raw name.
- The groundtruth's `/G1` resource key and `font00000000303895f2` naming scheme
  **exist nowhere in this repo's git history** (`git log -S` finds nothing) — so
  the groundtruth was produced by an older / different pipeline, not by any
  current-code build.

**Conclusion:** the groundtruth predates the font-decoding fixes. The current
output is more correct. No code change is warranted for the header; the
groundtruth must be regenerated.

### 2. Footer line — `/FreeText` annotation dropped (genuine bug, fixed)

The missing footer is the disclaimer

```
この資料は、受賞者に了解を得て、建築設備技術者協会より公開している資料です。個人で利用するに留め、無断転載等を禁止します。
```

(~61 chars = exactly the per-page char/word/line deltas). It is a `/FreeText`
annotation (confirmed via pikepdf) that has **no `/Type` key** — only
`/Subtype /FreeText`, `/Rect`, `/AP/N`, `/F 4` (Print).

The annotation dispatch in `src/parse/pdf_decoders/page.h` required
`/Type == "/Annot"` and `continue`d otherwise, silently dropping the annotation
before it could reach the appearance-rendering branch added in commit `09e5c4b`
("fixed the rendering of annotations"). The debug log confirmed this: it showed
neither `decoding the appearance of a /FreeText annotation` nor
`annot is being skipped`, which pins the drop to that `continue`.

Per ISO 32000-1 (12.5.2, Table 164), `/Type` is **optional** in an annotation
dictionary; membership in the page `/Annots` array plus a `/Subtype` is what
makes it an annotation.

**Fix applied** — `src/parse/pdf_decoders/page.h` (~line 1305): only reject a
`/Type` that is *present and* not `/Annot`:

```cpp
auto [has_type, type] = to_string(annot, "/Type");
if(has_type and type!="/Annot")
  {
    continue;
  }
```

Note: this guard is long-standing (commit `e7812a1`, Feb 2026), predating the
annotation-rendering commit — so the new FreeText-rendering branch was defeated
for any annotation lacking `/Type`.

## Why it splits macOS vs Ubuntu

- The groundtruth is downloaded from a **pinned HuggingFace dataset**
  (`tests/data_utils.py`, `HF_DATASET_REVISION`) — it is **not** git-tracked. It
  was generated once (on macOS); both platforms compare against that single
  artifact, so only macOS reproduces it.
- **FreeType is *not* involved.** `find_package(Freetype REQUIRED)` is only
  taken when `USE_SYSTEM_DEPS=ON`; the default is OFF, so both macOS and Linux
  build FreeType from source pinned at `VER-2-13-3`. More decisively, FreeType
  is referenced *only* under `src/render/` (`freetype_embedded_font_cache.h`,
  `blend2d_renderer.h`) and `src/pybind/docling_threaded_renderer.h` — there is
  no FreeType usage anywhere in `src/parse/`, which is the only code the parser
  regression test exercises. It cannot affect `font_key`, `font_name`, cell text
  or cell counts.
- The parser reads each page from a **QPDF-reserialized buffer**
  (`get_thread_safe_page_buffer` in `src/parse/pdf_decoders/document.h`), so
  whether the reserialized annotation carries `/Type /Annot` (and other
  normalization) depends on the QPDF/pipeline that produced the groundtruth.
  (QPDF is pinned to v12.2.0 and built from source via
  `cmake/extlib_qpdf_v12.cmake`; a page-copy with libqpdf 12.x preserves the
  `/R9` key and does **not** inject `/Type`.)

## Recommended actions

| Action | Where | Status |
|---|---|---|
| Relax the `/Type` guard so `/Type`-less annotations aren't dropped | `src/parse/pdf_decoders/page.h:1305` | ✅ done |
| **Regenerate the groundtruth** with current code on the CI (Ubuntu) toolchain, then bump `HF_DATASET_REVISION` | HF dataset + `tests/data_utils.py` | pending |
| ~~Pin FreeType so glyph decoding is identical across OSes~~ — already pinned (`VER-2-13-3`, built from source unless `USE_SYSTEM_DEPS=ON`), and unused by `src/parse/` | `cmake/extlib_freetype.cmake` | ❌ not applicable |
| (Optional) sanitize the raw Shift-JIS `font_name` currently emitted as mojibake | font layer | secondary |

The `/Type` fix alone will **not** make the test pass — the header mismatch is
purely the stale groundtruth. The durable fix is regenerating the groundtruth
with the current code.

## Post-fix verification (macOS, current build)

The `/Type` fix landed in `b1692c2`. Re-running the parser regression suite
leaves three failure classes, **all** explained above:

| Class | Documents | Cause |
|---|---|---|
| `len(true_hyperlinks)==len(pred_hyperlinks)`, 0 vs 1–2 | `082b97f3d239a9c5_0006.pdf`, `14770497121209673752.pdf`, … | `/Link` annotations with no `/Type`, now correctly emitted |
| `len(true_lines)==len(pred_lines)`, +1 line / +2 words / +19 chars per page | `8313873609013042575-4.pdf` (pages 1–5) | a `/Type`-less `/FreeText` stamp, now correctly rendered |
| `true_cell.font_key == pred_cell.font_key`, `/G1`≠`/R9`, `/G2`≠`/R13` | `15424333971388669153-2.pdf` | stale/foreign groundtruth (see §1) |

Each was checked against the raw PDF objects:

- **Hyperlinks.** Every newly-emitted hyperlink corresponds 1:1 to a `/Subtype
  /Link` annotation carrying a `/A << /S /URI >>` action, and the emitted `uri`
  and `rect` match the annotation's `/URI` and `/Rect` exactly. The groundtruth's
  `"hyperlinks": []` is the *dropped* state.
- **Text lines.** The one extra line per page of `8313873609013042575-4.pdf` is
  `ΑΔΑ: 6ΟΟΥ465ΧΙ8-ΟΑΘ`. Its 19 decoded characters reproduce the annotation's own
  `/Contents` string character-for-character, and the `Tj` in `/AP/N` holds
  exactly 19 two-byte glyph codes — so the appearance-stream decode is
  independently corroborated by `/Contents`. Same root cause as the hyperlinks.
- **Font keys.** `font_key` is assigned verbatim from
  `qpdf_fonts.getKeys()` (`src/parse/pdf_resources/page_fonts.h:136-145` →
  `page_font.set(key, …)` → `page_font.h:792`), i.e. it is *literally* the key in
  the page `/Resources /Font` dictionary. That dictionary reads
  `['/R9','/R13','/R17','/R23']` on page 1. No code path in the repo, at any
  revision, can synthesize `/G1`. The groundtruth for this document was produced
  from a **rewritten** copy of the PDF (sequential `/G1`,`/G2`,`/G3` keys with
  sequential `/AAAAAB+`,`/AAAAAC+`,`/AAAAAD+` subset tags), not from the file in
  `tests/data/regression/`.

**All three classes are the current code being right and the groundtruth being
stale.** The correct action is `--update-groundtruth`, followed by a diff review
and an `HF_DATASET_REVISION` bump.

## How to reproduce the investigation

```python
# compare current parse against the downloaded groundtruth
from docling_core.types.doc.page import SegmentedPdfPage

config = DecodeConfig(keep_glyphs=True, keep_qpdf_warnings=False, do_sanitization=True)
parser = DoclingPdfParser(loglevel="fatal")
doc = parser.load(path_or_stream="tests/data/regression/15424333971388669153-2.pdf",
                  boundary_type=PdfPageBoundaryType.CROP_BOX, lazy=True, decode_config=config)
tp = SegmentedPdfPage.load_from_json(
    "tests/data/groundtruth/parser/15424333971388669153-2.pdf.page_no_1.py.json")
pp = doc.get_page(1)
# diff tp.textline_cells vs pp.textline_cells (text / font_key / rect)
```
